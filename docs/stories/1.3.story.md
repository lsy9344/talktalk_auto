## Story

**As a** 시스템 운영자(프로젝트 오너),
**I want** 전체 시스템 구성(AWS 서비스들)과 데이터 흐름을 한 문서로 보기 쉽게 정리하고,
**so that** 개발/운영 때 모두 같은 그림을 보고 안전하게 개발할 수 있다.

## Acceptance Criteria

1. 시스템이 사용하는 AWS 구성요소가 문서에 정리되어 있다: API Gateway, Lambda(Ingest/Worker/Indexer), SQS, DynamoDB, S3, EventBridge Scheduler, SSM Parameter Store. [Source: docs/prd/epic-1-core-infrastructure-channel-routing.md#story-13-시스템-개요architecture]
2. 기본 데이터 흐름이 문서에 명확히 적혀 있다: Webhook → API Gateway → Ingest → SQS → Worker → (Sheets/Telegram) → (조건부 TalkTalk send). [Source: docs/architecture.md#high-level-overview]
3. DynamoDB가 어떤 데이터를 저장하는지(최소: ChannelConfig, GlobalMode 또는 SSM, Dedup)가 설명되어 있다. [Source: docs/prd/epic-1-core-infrastructure-channel-routing.md#story-13-시스템-개요architecture]
4. S3 / EventBridge Scheduler의 역할(문서 동기화, 벡터 인덱스 저장)이 설명되어 있다. [Source: docs/prd/epic-1-core-infrastructure-channel-routing.md#story-13-시스템-개요architecture]
5. SSM Parameter Store(SecureString)에 어떤 값을 저장하는지(OpenAI, 톡톡 Authorization, Google SA, Telegram)가 설명되어 있다. [Source: docs/prd/epic-1-core-infrastructure-channel-routing.md#story-13-시스템-개요architecture]

### 용어(쉬운 설명)

[Source: docs/architecture.md#high-level-overview]

- **Ingest**: 톡톡(Webhook) 요청을 “빠르게 받고” SQS에 넣는 Lambda
- **Worker**: SQS 메시지를 받아서 RAG/LLM/기록/알림을 하는 Lambda
- **Indexer**: Google Docs를 주기적으로 읽어서(동기화) 벡터 인덱스를 만드는 Lambda

### 문서에서 꼭 확인할 내용(요약)

[Source: docs/architecture.md#high-level-architecture]
[Source: docs/architecture.md#high-level-overview]
[Source: docs/architecture.md#high-level-project-diagram]

- **구성요소:** API Gateway, Lambda(Ingest/Worker/Indexer), SQS, DynamoDB, S3, EventBridge Scheduler, SSM Parameter Store
- **기본 흐름:** Webhook → Ingest(빠른 200 OK) → SQS → Worker(처리) → Sheets 기록/Telegram 알림/조건부 자동발송
- **문서 동기화 흐름:** EventBridge Scheduler → Indexer → Google Docs fetch → (임베딩/인덱스) → S3 저장
