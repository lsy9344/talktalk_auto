# Story 7.2: PROD 전환 전 "안전장치"

## Status

Done

## Story

**As a** 시스템 운영자(프로젝트 오너),
**I want** PROD 전환 전에 “안전장치(보수적 threshold, HIGH 리스크 차단, echo 루프 방지)”를 코드/설정/테스트로 고정하고,
**so that** 고객에게 잘못 자동 발송하거나 무한 루프가 나는 사고를 줄일 수 있다.

## Background & Context

Epic 7은 “테스트/운영 준비”를 다룹니다. Story 7.2는 “PROD로 올리기 전에 미리 걸어두는 안전장치”입니다.

PRD가 말하는 핵심 안전장치는 아래 3가지입니다:

1. threshold를 높게(보수적으로) 시작: **0.85 권장**
2. `risk_level == HIGH`는 **무조건 무응답 + 알림**
3. `echo` 이벤트는 **비활성 유지** (루프 위험)

## Acceptance Criteria

### AC1: PROD 전환 초기에는 threshold(신뢰도 기준)를 0.85로 보수적으로 시작한다

- ChannelConfig에 `confidence_threshold`가 있어야 한다. [Source: docs/architecture.md#channelconfig-채널-설정]
- PROD 전환을 시작하는 채널은 `confidence_threshold=0.85`를 기본값으로 사용한다. (운영자가 이후 튜닝 가능) [Source: docs/prd/112-prod-전환-전-안전장치.md]
- **실수 방지(누락 케이스만):** ChannelConfig에 `confidence_threshold`가 **누락된 경우에만**, 코드에서 안전하게 0.85를 기본값으로 처리한다. (누락으로 0.80 기본값이 들어가 자동 발송이 쉬워지는 상황을 막기) [Source: docs/architecture.md#decision-logic-implementation]
- `confidence_threshold`가 **명시되어 있으면 그 값을 그대로** 사용한다. (튜닝 가능해야 함) [Source: docs/prd/112-prod-전환-전-안전장치.md]

[Source: docs/prd/52-자동-발송sendtousertrue-허용-조건.md]
[Source: docs/architecture.md#prod-mode-three-gate-system]

### AC2: `risk_level == HIGH`는 PROD에서도 무조건 무응답 + Telegram 알림이다

- Global/Channel이 PROD여도, LLM 결과가 `risk_level == HIGH`면 `send_to_user=false`로 막는다. [Source: docs/prd/52-자동-발송sendtousertrue-허용-조건.md] [Source: docs/prd/72-developer-prompt-정책스키마-강제.md]
- 이 경우 “무응답 + Telegram 알림” 흐름이 보장되어야 한다. [Source: docs/prd/53-무응답-telegram-알림-트리거운영자-개입-필요.md] [Source: docs/architecture.md#telegram-alert-triggers]

### AC3: `echo` 이벤트는 처리하지 않고 200 OK로 끝낸다(루프 방지)

- Ingest는 `event != "send"`면 **SQS enqueue 없이** 200 OK를 반환한다. (특히 `echo`는 루프 위험이 크다) [Source: docs/architecture.md#naver-talktalk-webhook-api]
- 운영 관점에서도 파트너센터에서 `echo` 이벤트는 기본 비활성 상태를 유지한다. [Source: docs/prd/2-외부-연동-제약네이버-톡톡.md#24-이벤트루프-위험echo]

### AC4: 테스트가 있고 통과한다

최소 아래를 테스트로 막는다:

- PROD + Channel PROD + `confidence_threshold` 누락 시, threshold를 0.85로 처리하는지 (0.83이면 발송 차단, 0.86이면 조건 통과 가능) [Source: docs/architecture.md#decision-logic-implementation]
- PROD + Channel PROD + `risk_level == HIGH`면 confidence가 높아도 발송이 막히고, 알림 이유에 HIGH 리스크가 포함되는지 [Source: docs/architecture.md#telegram-alert-triggers]
- Ingest에서 `echo` 이벤트가 들어오면 200 OK로 끝나고 enqueue 하지 않는지 [Source: docs/architecture.md#naver-talktalk-webhook-api]

[Source: docs/architecture/coding-standards.md#test-strategy-and-standards]

### Echo 이벤트(루프 위험) 요약

- `echo` 이벤트는 “우리가 보낸 메시지”도 다시 들어올 수 있어 무한 루프 위험이 있습니다.
- 운영 안정성을 위해 파트너센터에서 echo 이벤트를 기본 비활성으로 두는 것을 권장합니다.
- 코드에서도 `event != send`는 무시(200 OK)하여, echo가 들어와도 enqueue 되지 않게 합니다.

[Source: docs/prd/2-외부-연동-제약네이버-톡톡.md#24-이벤트루프-위험echo]
