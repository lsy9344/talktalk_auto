# Story 7.1: TEST 모드 필수 통과 조건

## Status

Done

## Story

**As a** 시스템 운영자(프로젝트 오너),
**I want** TEST 모드에서 “반드시 통과해야 하는 조건”을 코드/테스트/운영 절차로 확인할 수 있게 만들고,
**so that** PROD 전환 전에 실수(자동 발송/로그 누락/알림 누락/웹훅 타임아웃)를 미리 막을 수 있다.

## Background & Context

Epic 7은 “테스트/운영 준비”를 다룹니다. 그 첫 단계가 Story 7.1 입니다.

PRD에서 말하는 TEST 모드 필수 통과 조건은 아래 4가지입니다:

1. 톡톡으로 **자동 발송 0건**
2. `send` 이벤트 수신 시 **Sheets row 100% 생성**
3. 불확실/오류 케이스에서 Telegram 알림이 **누락 없이 도착**
4. Webhook은 타임아웃 없이 안정적으로 200 OK 반환(3s/5s 제약 준수)

[Source: docs/prd/111-test-모드-필수-통과-조건.md]
[Source: docs/prd/epic-7-testing-production-deployment.md#story-71-test-모드-필수-통과-조건]

## Acceptance Criteria

### AC1: TEST 모드에서는 자동 발송이 0건이다

- 아래 중 하나라도 TEST이면 “TEST 모드”로 본다:
  - `global_mode == TEST`
  - `channel_mode == TEST`
- TEST 모드에서는 고객 발송(TalkTalk Send API 호출)을 **절대 하지 않는다**.
- 이 규칙이 테스트로 고정되어야 한다.

[Source: docs/architecture.md#test-vs-prod-mode-behavior]

### AC2: `send` 이벤트는 Sheets row를 100% 만든다(최소: append 시도 + 실패 시 알림)

- Worker는 `send` 이벤트를 처리할 때, `inbox_log`에 1줄을 남긴다.
- Sheets 기록 실패(E005)가 나면:
  - 시스템은 멈추지 않되,
  - 운영자가 알 수 있도록 Telegram 알림(또는 최소 알림 시도)을 한다.
- 위 흐름이 테스트로 고정되어야 한다.

### AC3: 불확실/오류 케이스에서 Telegram 알림이 누락 없이 도착한다(최소: 호출/예외 처리 보장)

- TEST 모드에서는 “항상 알림”이다.
- PROD 모드에서도 아래 같은 케이스는 알림 대상이다:
  - RAG 근거 부족
  - HIGH 리스크
  - 외부 API 실패(E004/E005/E006)
- Telegram 전송 실패는 시스템을 멈추지 않고 로그만 남긴다(알림 실패로 서비스 중단 금지).
- 위 흐름이 테스트로 고정되어야 한다.

### AC4: Webhook은 3초/5초 제한을 넘기지 않고 안정적으로 200 OK를 반환한다

- Connection timeout 3초 / Read timeout 5초 제약이 있다.
- Ingest는 “웹훅 요청 처리” 안에서 느린 작업(OpenAI/Google Sheets/Telegram)을 하지 않는다.
- 정상 `send` 이벤트는 SQS enqueue 후 바로 200 OK를 반환한다. (무거운 처리는 Worker가 비동기로 수행)
- 이 규칙이 테스트로 고정되어야 한다.

[Source: docs/architecture.md#naver-talktalk-webhook-api]
[Source: docs/architecture.md#aws-components-summary]

[Source: docs/stories/1.2.story.md]

### AC5: 테스트가 있고 통과한다

최소 아래를 테스트로 막는다:

- TEST 모드에서 TalkTalk Send API 호출이 0번인지
- `send` 이벤트에서 Sheets append가 호출되는지 (실패 시 Telegram 알림 이유에 E005가 포함되는지)
- TEST 모드에서 Telegram 알림 호출이 항상 일어나는지
- Ingest가 `send` 이벤트에서 200 OK를 반환하고, Worker 작업을 하지 않는지(= SQS enqueue만 하는지)

[Source: docs/architecture/coding-standards.md#test-strategy-and-standards]

## Dev Notes

### TEST 모드에서 기대 동작(요약)

- TEST 모드:
  - 고객에게는 **절대 발송하지 않음**
  - 모든 메시지는 Google Sheets에 기록
  - 운영자에게 Telegram 알림 (테스트 확인용)

[Source: docs/architecture.md#test-vs-prod-mode-behavior]

### Webhook 타임아웃 제약(왜 Ingest는 빨라야 하나)

- 톡톡 Webhook은 타임아웃이 매우 짧습니다:
  - Connection timeout 3초
  - Read timeout 5초
- 그래서 Ingest는 “검증 + SQS enqueue + 즉시 200 OK”만 하고,
  무거운 처리는 Worker가 비동기로 해야 안전합니다.

[Source: docs/architecture.md#naver-talktalk-webhook-api]
[Source: src/functions/ingest/app.py]

### 자동 발송 0건을 보장하는 코드 포인트

- 3-gate 의사결정에서 global_mode 또는 channel_mode가 TEST면 send_to_user는 False가 됩니다. [Source: src/functions/worker/decision.py]
- 실제 발송은 `send_answer_if_allowed()`가 책임지고, send_to_user가 False면 TalkTalk API를 호출하지 않습니다. [Source: src/functions/worker/send_answer.py]

### Sheets row 생성 관련 코드 포인트

- Sheets append는 `GoogleSheetsClient.append_log_row()`로 합니다. (재시도 + Circuit Breaker 포함) [Source: src/layers/shared/python/talktalk_shared/clients/google_sheets_client.py]
- Worker 파이프라인에서는 Sheets 실패(E005)를 잡아 Telegram 알림 reasons에 추가합니다. [Source: src/functions/worker/pipeline.py] [Source: docs/architecture.md#에러-처리-패턴]

### Telegram 알림 관련 코드 포인트

- TEST 모드면 `evaluate_alert_triggers()`가 무조건 `should_alert=True`를 돌려줍니다. [Source: src/functions/worker/alert_rules.py]
- Telegram 전송 실패는 시스템을 멈추지 않고 로그만 남깁니다. [Source: docs/architecture.md#telegram-bot-api] [Source: src/layers/shared/python/talktalk_shared/clients/telegram_client.py]

### Testing

- pytest 사용, AAA 패턴(Arrange/Act/Assert) [Source: docs/architecture/coding-standards.md#test-strategy-and-standards]
- 외부 의존성(DynamoDB, SQS, Google APIs, Telegram)은 모두 모킹 [Source: docs/architecture/coding-standards.md#test-strategy-and-standards]
- 테스트 파일 규칙:
  - 유닛: `tests/unit/test_{module}.py`
  - 통합: `tests/integration/test_{lambda_name}_lambda.py`

[Source: docs/architecture/coding-standards.md#coding-standards]
