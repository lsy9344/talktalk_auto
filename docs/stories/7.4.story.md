# Story 7.4: 구현자에게 중요한 메모(실수 방지)

## Status

Done

## Story

**As a** 시스템 개발자(구현자),
**I want** 네이버 톡톡(TalkTalk) 연동에서 자주 실수하는 포인트를 한 문서로 정리하고(필요한 건 테스트로도 고정하고),
**so that** 운영/배포 전에 실수로 장애나 루프(무한 반복)를 만드는 일을 줄일 수 있다.

## Background & Context

PRD에는 “구현자에게 중요한 메모(실수 방지)”로 아래 4가지가 강조되어 있습니다:

1. `user_id`는 변하지 않는 사용자 식별값 → 상태/중복방지 키 설계에 사용
2. `send` 이벤트로 “보내기 API”를 호출할 때는 text/image/composite 중 **하나만 선택**
3. `echo` 이벤트는 루프 위험 → 기본 비활성 권장
4. Webhook 타임아웃(3s/5s) 때문에 “즉시 200 OK + 비동기”가 안전

이 Story는 위 4가지를 “한 문서”로 모아, 새로 참여한 개발자도 빠르게 이해할 수 있게 만드는 것이 목적입니다.

## Dependencies

- Webhook은 “즉시 ACK(200 OK로 바로 응답) + SQS(메시지 큐)에 넣기(enqueue)” 패턴을 이미 사용합니다. [Source: docs/architecture.md#naver-talktalk-webhook-api] [Source: docs/stories/1.2.story.md]
- `echo/open/leave` 같은 non-send 이벤트는 무시(200 OK)하도록 이미 구현/테스트가 있습니다. [Source: docs/architecture.md#naver-talktalk-webhook-api] [Source: docs/stories/7.2.story.md]
- Send API 호출은 `TalkTalkClient`로 캡슐화되어 있고, 이미 유닛 테스트가 있습니다. [Source: docs/architecture.md#naver-talktalk-send-api] [Source: src/layers/shared/python/talktalk_shared/clients/talktalk_client.py] [Source: tests/unit/test_talktalk_client.py]

### AC2: `user_id` 관련 실수 포인트가 문서에 정리되어 있다

문서에 아래 내용이 들어있다:

- `user_id`는 변하지 않는 사용자 식별값이라는 점을 명시한다. [Source: docs/prd/13-구현자에게-중요한-메모실수-방지.md]
- 중복 방지(DeduplicationRecord)의 키가 `{channel_id}#{user_id}#{message_hash}` 형태라는 점을 함께 적는다. [Source: docs/architecture.md#deduplicationrecord-중복-방지]

### AC3: “보내기 API”의 메시지 타입 선택 규칙이 문서/테스트로 고정된다

- 문서에 “`send`로 보낼 때는 text/image/composite 중 1개만 선택” 규칙이 들어있다. [Source: docs/prd/13-구현자에게-중요한-메모실수-방지.md]
- 현재 구현은 `textContent`만 보내는 형태라는 점을 문서에 적는다. [Source: docs/architecture.md#naver-talktalk-send-api] [Source: src/layers/shared/python/talktalk_shared/clients/talktalk_client.py]
- 유닛 테스트에서 `send_text_message()`가 **오직 `textContent`만** 포함하도록 검증한다. (예: `imageContent`/`compositeContent` 키가 없는지 확인) [Source: tests/unit/test_talktalk_client.py] [Source: docs/architecture/coding-standards.md#test-strategy-and-standards]

### AC4: `echo` 이벤트의 루프 위험과 처리 원칙이 문서에 정리되어 있다

- 문서에 아래가 명확히 적혀 있다:
  - `echo`는 “우리가 보낸 메시지가 다시 들어올 수 있음” → 무한 루프 위험 [Source: docs/architecture.md#naver-talktalk-webhook-api]
  - 권장: 파트너센터에서 `echo` 이벤트 비활성화 [Source: docs/architecture.md#naver-talktalk-webhook-api]
  - 코드에서는 `event != "send"`면 200 OK로 끝내고 SQS에 넣기(enqueue)도 하지 않는다는 점 [Source: docs/architecture.md#naver-talktalk-webhook-api]

### AC5: Webhook 타임아웃(3s/5s)과 “즉시 ACK + 비동기” 원칙이 문서에 정리되어 있다

- 문서에 아래가 명확히 적혀 있다:
  - TalkTalk Webhook 타임아웃: connection 3초 / read 5초 [Source: docs/architecture.md#naver-talktalk-webhook-api]
  - 따라서 5초 안에 200 OK를 반환해야 한다 [Source: docs/architecture.md#naver-talktalk-webhook-api]
  - 처리(30~120초)는 Worker Lambda(비동기 처리 담당)에서 비동기(나중에 처리)로 한다 [Source: docs/architecture.md#naver-talktalk-webhook-api]

### AC6: 전체 테스트가 통과한다

- `python3 -m pytest -q`가 통과한다. [Source: docs/architecture/coding-standards.md#test-strategy-and-standards]

### Data Models

- DeduplicationRecord:
  - `dedup_key = "{channel_id}#{user_id}#{message_hash}"`
  - TTL 10분 [Source: docs/architecture.md#deduplicationrecord-중복-방지]

### API Specifications

- Webhook (Inbound):
  - timeout: connection 3s / read 5s
  - event: `send/open/leave/echo`
  - `echo`는 루프 위험 → 권장 비활성 [Source: docs/architecture.md#naver-talktalk-webhook-api]
- Send API (Outbound):
  - `POST https://gw.talk.naver.com/chatbot/v1/event`
  - Headers: `Authorization: {CHANNEL_AUTH_TOKEN}`
  - Body 예시: `"event":"send"`, `"user":"{user_id}"`, `"textContent":{"text":"..."}` [Source: docs/architecture.md#naver-talktalk-send-api]
