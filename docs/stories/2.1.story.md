## Status

## Story

**As a** 시스템 운영자(프로젝트 오너),
**I want** 메시지 처리 과정을 단계(상태)로 나누고 코드로 고정해서,
**so that** 한 건의 메시지가 지금 어디까지 처리됐는지 쉽게 추적(디버깅)할 수 있다.

## Acceptance Criteria

1. 파이프라인 상태 값 8개가 코드로 한 곳에 정의되어 있다: `RECEIVED`, `QUEUED`, `PROCESSING`, `LOGGED`, `SENT`, `NOT_SENT`, `ALERTED`, `FAILED`. [Source: docs/prd/51-파이프라인-상태-머신.md] [Source: docs/prd/epic-2-message-processing-pipeline.md#story-21-파이프라인-상태-머신]
2. “상태 전환(transition)” 규칙이 정의되어 있고, 최소 정상 흐름은 아래 순서를 따른다: `RECEIVED → QUEUED → PROCESSING → LOGGED → (SENT 또는 NOT_SENT)` (필요 시 `ALERTED`, 오류 시 `FAILED`). [Source: docs/architecture.md#core-workflows] [Source: docs/architecture.md#components]
3. Ingest Lambda가 SQS에 넣는 메시지에 `pipeline_state`를 포함한다(최소 `QUEUED`). 이 값은 Enum 객체가 아니라 **문자열 값**(예: `"QUEUED"`)로 넣는다. 중복/무시 이벤트는 enqueue하지 않으므로 `QUEUED`가 되지 않는다. [Source: docs/architecture.md#components] [Source: docs/architecture.md#high-level-overview]
4. 파이프라인 상태 구현은 Shared Layer(`talktalk_shared`)에 두어, Ingest/Worker가 같은 값을 재사용한다(문자열 하드코딩 최소화). [Source: docs/architecture/source-tree.md]
5. 유닛 테스트로 상태 전환 규칙과 Ingest 메시지 `pipeline_state` 포함을 확인한다(AAA 패턴, pytest). [Source: docs/architecture/coding-standards.md#test-strategy-and-standards]

### 용어(쉬운 설명)

[Source: docs/prd/51-파이프라인-상태-머신.md]

- **파이프라인**: 메시지가 들어와서(수신) 처리되고(Worker), 기록되고(Sheets), 필요하면 발송/알림까지 가는 “전체 흐름”
- **상태(State)**: 지금 흐름의 어느 단계인지 나타내는 값

### 상태 정의(언제 어떤 값이 되나)

[Source: docs/prd/51-파이프라인-상태-머신.md]
[Source: docs/architecture.md#core-workflows]

- `RECEIVED`: Ingest가 유효한 `send` 이벤트를 받아서 처리 시작
- `QUEUED`: Ingest가 SQS enqueue를 성공함
- `PROCESSING`: Worker가 SQS 메시지를 받아 처리 시작
- `LOGGED`: Worker가 Google Sheets에 로그를 남김
- `SENT`: (PROD에서) TalkTalk Send API 발송 성공
- `NOT_SENT`: 정책상 무응답(예: TEST 모드, 게이트 실패)
- `ALERTED`: Telegram 알림 전송 성공
- `FAILED`: 재시도 후 실패 또는 DLQ로 이동하는 실패 상황

### 상태 전환 규칙(간단 표)

[Source: docs/prd/51-파이프라인-상태-머신.md]
[Source: docs/architecture.md#core-workflows]

- 정상 흐름(기본): `RECEIVED → QUEUED → PROCESSING → LOGGED → (SENT 또는 NOT_SENT)`
- 알림이 필요하면: `LOGGED → ALERTED` (예: 무응답/에러라서 운영자 알림을 보낸 경우)
- 에러가 나면: 처리 중 어느 단계에서든 `FAILED`로 갈 수 있다 (예: 예외 발생, 재시도 후 실패)
