# Story 3.3: Chunking 권장 규칙 (제목/소제목 + 메타데이터)

## Status

Ready for Review

## Story

**As a** 시스템 운영자(프로젝트 오너),
**I want** KB 문서를 “제목/소제목 기준”으로 나누고(Chunking) 각 조각에 메타데이터를 붙여서,
**so that** RAG가 근거를 더 잘 찾고, 나중에 답변에 “어디 문서의 어느 부분인지” 표시(citations)도 할 수 있다.

## Background & Context

Indexer는 Google Docs 문서를 읽어서 **청크(조각)** 로 나눈 뒤, 각 청크로 임베딩을 만들고 FAISS 인덱스를 생성합니다.

- 청크가 너무 크면(길면) 한 번에 넣을 때 비용/성능이 나빠질 수 있습니다.
- 청크가 너무 작으면 문맥이 끊겨서 검색 품질이 떨어질 수 있습니다.
- 그래서 **대략 400~800 tokens** 정도 크기가 권장됩니다.
- 또한 청크마다 `doc_id`, `doc_title`, `section_path` 같은 메타데이터가 있어야 “어느 근거를 썼는지”를 표시하기 쉽습니다.

[Source: docs/prd/63-chunking-권장-규칙.md]
[Source: docs/architecture.md#lambda-indexer-문서-동기화]
[Source: docs/architecture.md#워크플로-4-주간-문서-동기화]

### Dependencies

- Story 3.2(Indexer + chunking 기본) 완료가 필요합니다. [Source: docs/stories/3.2.story.md]
- Google Docs API로 `GET /documents/{documentId}`를 사용합니다. (body.content, revisionId, modifiedTime) [Source: docs/architecture.md#google-docs-api]

## Acceptance Criteria

### AC1: 제목/소제목 기준으로 먼저 나누고, 400~800 tokens 근처로 청킹한다

- 문서에서 “제목/소제목(heading)”을 기준으로 먼저 섹션을 나눈다.
- 각 섹션 안에서 청크 크기는 **대략 400~800 tokens** 근처가 되도록 만든다.
  - (주의) 여기서 tokens는 정확한 토큰 라이브러리가 없으면 “단어 개수/문자 수”로 근사해도 된다. (단, 범위에 최대한 맞춘다) (추가 규칙: 팀 결정)

[Source: docs/prd/63-chunking-권장-규칙.md]
[Source: docs/architecture.md#워크플로-4-주간-문서-동기화]
[Source: docs/architecture/tech-stack.md]

### AC2: 각 청크에 메타데이터가 포함된다

각 청크는 아래 메타데이터를 가진다:

- `doc_id`
- `doc_title`
- `section_path` (예: `대제목 > 소제목 > ...` 형태)
- `updated_at` (가능하면 Google Docs의 modifiedTime 기반)
- `channel_id/common`
  - 문서가 “공통 KB”면 `common`
  - 공통 KB가 아니면 `channel_id`
  - (예외) 같은 `doc_id`가 여러 채널에 걸쳐 있으면, `channel_id`는 **정해진 규칙**(예: channel_id 정렬 후 첫 번째)으로 1개만 고르고 경고 로그를 남긴다 (추가 규칙: 팀 결정)
- `chunk_id` (문서 안에서 유일한 값)

[Source: docs/prd/63-chunking-권장-규칙.md]
[Source: docs/architecture.md#google-docs-api]

### AC3: chunk_id는 “결정적(deterministic)”이고, 같은 문서면 순서가 안정적이다

- 같은 문서 내용이 같으면 chunk_id/순서가 매번 바뀌지 않는다.
- 예: `c_001`, `c_002` 처럼 1부터 증가하는 형태(또는 비슷한 안정적인 규칙).

### AC4: Indexer가 청크 텍스트로 임베딩을 만들고, 청크 메타데이터를 함께 저장한다

- Indexer는 청크 텍스트로 임베딩을 만들고(FAISS 인덱스 생성), 청크 개수를 메타데이터에 반영한다.
- 청크 메타데이터(필요하면 텍스트 포함)는 Worker가 나중에 쓸 수 있게 저장된다.

[Source: docs/architecture.md#lambda-indexer-문서-동기화]
[Source: docs/architecture.md#vectorindexmetadata-벡터-인덱스-메타데이터]

### AC5: 테스트가 있고 통과한다

최소 아래는 테스트로 검증한다:

- 제목/소제목 기준 분리가 기대대로 동작한다
- 청크 크기가 400~800 tokens “근처”로 만들어진다 (근사 기준 포함)
- 청크 메타데이터 필드가 빠지지 않는다
- chunk_id가 안정적이다(같은 입력이면 같은 결과)

[Source: docs/architecture/coding-standards.md#test-strategy-and-standards]

### Previous Story Insights

- Story 3.2에서 `DocumentChunker`는 현재 “문자 기준(800 chars + overlap)”으로만 나눕니다. 이번 Story 3.3에서 “제목/소제목 기준 + tokens 근처” 규칙으로 개선이 필요합니다. [Source: docs/stories/3.2.story.md]
