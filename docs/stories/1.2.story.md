# Story 1.2: 네이버 톡톡 Webhook 수신(Ingest) 구축 (Naver TalkTalk Webhook Ingest Setup)

## Status

Done

## Story

**As a** 시스템 운영자(프로젝트 오너),
**I want** 네이버 톡톡(Webhook) 이벤트를 빠르고 안전하게 받아서 SQS로 넘기는 Ingest 엔드포인트를 만들고,
**so that** 톡톡의 짧은 타임아웃(3초/5초)을 지키면서도, 실제 처리는 비동기로 안정적으로 진행할 수 있다.

## Acceptance Criteria

1. `POST /naver/talktalk/{channel_id}/webhook` 요청이 Ingest Lambda로 들어오고, 톡톡 타임아웃을 넘기지 않게 빠르게 응답한다. (목표: 정상 케이스 500ms 이하, 최종 마지노선 5초 이내 200 OK)  
2. Webhook Body(JSON)를 Pydantic 모델로 검증한다. 검증 실패 시 400을 반환한다.  
3. URL의 `channel_id`로 ChannelConfig를 조회한다. ChannelConfig가 없거나 `enabled == false` 또는 `channel_mode == "DISABLED"`면 404를 반환한다.  
4. `event == "send"`만 처리한다. `open/leave/echo` 등은 200 OK로 바로 끝내고 SQS에 넣지 않는다. (echo는 무한 루프 위험 때문에 특히 주의)  
5. 처리 대상(`send`)은 SQS에 메시지를 넣고 200 OK를 반환한다. SQS 메시지는 최소한 `channel_id`와 webhook 원문(또는 필요한 필드들)을 포함한다.  
6. 톡톡 재시도 때문에 같은 메시지가 반복 들어올 수 있으므로, 10분 TTL 기반으로 중복을 감지해 “중복이면 SQS enqueue를 건너뛰고 200 OK”로 처리한다.  
7. 아래 케이스를 테스트로 확인한다: 정상 send, 스키마 오류, 채널 없음/비활성, echo(또는 send가 아닌 이벤트) 무시, 중복 이벤트 스킵, SQS 실패 시 500 반환.

### Ingest Lambda가 해야 하는 일 / 하면 안 되는 일

[Source: docs/architecture.md#Naver TalkTalk Webhook API]

해야 하는 일(가벼운 것만):
1. 스키마 검증 (pydantic)
2. ChannelConfig 로드(채널 존재/활성 확인)
3. 이벤트 타입 필터링(`send`만 처리, `echo` 등 무시)
4. (권장) 중복 방지(DynamoDB TTL)

- LLM 호출
- Google Sheets 기록
- 복잡한 비즈니스 로직

### Dedup(중복 방지) 규칙

[Source: docs/architecture.md#Naver TalkTalk Webhook API]

- 톡톡은 네트워크 문제 시 webhook을 재시도할 수 있습니다.
- 10분 TTL의 DeduplicationRecord를 사용해 중복을 걸러냅니다.
- 중복이면 “200 OK는 주되, SQS enqueue는 하지 않기”가 안전합니다.
- 권장 키 구성:
  - PK: `dedup_key = "{channel_id}#{user_id}#{message_hash}"`
  - TTL: 10분 (DynamoDB TTL Attribute: `ttl`)
  - `message_hash`는 webhook body 전체를 기준으로 만든다(재시도 중복 방지 목적):
    - 1) Body dict를 “키 정렬된 JSON 문자열”로 만든다 (`json.dumps(body, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`)
    - 2) 그 문자열을 `sha256()` 하고 앞 16글자를 쓴다 (`hexdigest()[:16]`)

참고: 현재 문서/예시에는 webhook payload에 메시지 고유 ID / timestamp 필드가 보이지 않는다. 그래서 이번 Story에서는 “payload 전체 해시”로 중복을 판단한다. 추후 공식 필드가 확인되면 dedup 키 규칙을 더 정확하게 개선할 수 있다.

### Echo 이벤트 주의

[Source: docs/architecture.md#Naver TalkTalk Webhook API]

- echo 이벤트는 우리가 보낸 메시지를 다시 받을 수 있어 무한 루프 위험이 있습니다.
- 기본 권장은 파트너센터에서 echo 이벤트를 꺼두는 것입니다.
- 그래도 들어오면 Ingest에서 바로 무시(200 OK) 처리합니다.
