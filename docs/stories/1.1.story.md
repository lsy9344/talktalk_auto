### Key Technical Constraints from Architecture

**Naver TalkTalk API Constraints** [Source: docs/architecture.md#External APIs]:
- Webhook timeout: Connection 3s / Read 5s
- Requires immediate 200 OK response
- Authorization via channel-specific tokens (stored in SSM Parameter Store)
- Send API endpoint: `POST https://gw.talk.naver.com/chatbot/v1/event`
- Echo events should be disabled to prevent infinite loops

**Cost Optimization Focus** [Source: docs/architecture.md#High Level Architecture]:
- Target volume: 10-30 messages/day (~300-900 messages/month)
- Expected monthly cost: $2-4/month
- Lambda operates in free tier (1M requests/month)
- Primary cost is OpenAI API (~$0.50-1.50/month for gpt-4o-mini)

**Dual-Mode Safety Design** [Source: docs/architecture.md#High Level Architecture]:
- **TEST Mode** (default): No auto-send, log to Sheets only, Telegram alerts for uncertain cases
- **PROD Mode**: Requires THREE conditions:
  1. Global mode = PROD
  2. Channel mode = PROD
  3. LLM confidence score meets threshold (send_to_user=true)

**Architecture Patterns** [Source: docs/architecture.md#Architectural and Design Patterns]:
- Serverless Architecture (AWS Lambda pay-per-invocation)
- Event-Driven Architecture (Webhook → SQS → Worker)
- Repository Pattern (DynamoDB abstraction)
- Strategy Pattern (TEST/PROD mode logic)
- Circuit Breaker Pattern (external API calls)
- Idempotency Pattern (deduplication via DynamoDB TTL)

### Customer Communication Policies (Critical - Must Document)

From Epic 1.1 [Source: docs/prd/epic-1-core-infrastructure-channel-routing.md]:

**Prohibited Responses** (NEVER send to customers):
- "모르겠습니다" (I don't know)
- "애매합니다" (It's ambiguous)
- "추측입니다" (This is a guess)
- "상담원에게 연결할게요" (I'll connect you to an agent)

**Handling Uncertain Cases**:
- Customer: NO RESPONSE (silent)
- Operator: Telegram alert with:
  - Channel name
  - Customer ID (masked)
  - Question summary
  - Draft response (if any)
  - Reason for flagging

### Data Models Referenced (For Context Only)

[Source: docs/architecture.md#Data Models]

The system will use 4 DynamoDB tables:
1. **ChannelConfig**: Channel settings, doc mappings, TEST/PROD mode per channel
2. **GlobalMode**: Master switch for entire system (TEST/PROD)
3. **DeduplicationRecord**: Prevent duplicate webhook processing (10-min TTL)
4. **VectorIndexMetadata**: Track Google Docs sync status and S3 index locations

**Note**: These tables do NOT need to be created in this story - they are defined in architecture for future implementation.

### Testing

**Testing Strategy** [Source: docs/architecture/coding-standards.md#Test Strategy and Standards]:

Since this is a documentation-only story, there are no code tests required. However, the following testing standards should be documented for future development:

**Test Framework**: pytest 7.4.3+
**Test Structure**:
- Unit tests: `tests/unit/test_{module}.py`
- Integration tests: `tests/integration/test_{lambda_name}_lambda.py`
- Fixtures: `tests/fixtures/` for mock data

**Coverage Requirements**:
- Unit tests: 80% coverage for core logic
- Integration tests: Cover main workflows
- Test pyramid: 70% unit : 25% integration : 5% E2E

**Mandatory Testing Patterns**:
- AAA pattern (Arrange, Act, Assert)
- All external dependencies must be mocked (DynamoDB, OpenAI, Google APIs)
- Edge cases: empty values, None, empty lists, exceptions

**CI/CD Testing Pipeline**:
1. Linting (ruff, mypy)
2. Unit tests (parallel execution)
3. Integration tests
4. Coverage report (80% minimum enforced)
