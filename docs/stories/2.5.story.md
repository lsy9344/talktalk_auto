# Story 2.5: Message Aggregation (30초 타임 윈도우)

## Status

Draft

## Story

**As a** 고객 서비스 시스템 운영자,
**I want** 동일 사용자의 여러 메시지를 30초 동안 수집하여 하나의 질문으로 조합 후 처리하고,
**so that** 고객이 질문을 여러 번 나눠 보내도 전체 문맥을 이해하여 정확한 답변을 제공할 수 있다.

## Background & Context

### 문제 상황

고객이 하나의 질문을 여러 개의 메시지로 나눠서 보내는 패턴 발견:

**예시:**
```
메시지 1 (10:30:00): "안녕하세요"
메시지 2 (10:30:05): "내일 예약하려고 하는데"
메시지 3 (10:30:10): "인화지가 총"
메시지 4 (10:30:15): "몇장 제공되는지"
메시지 5 (10:30:20): "문의드려요"
```

**현재 시스템 동작:**
- 각 메시지를 독립적으로 처리
- 5번의 RAG + LLM 호출
- 문맥 손실로 인한 응답 품질 저하
- 불필요한 중간 응답 발송

### 목표 솔루션

30초 타임 윈도우 기반 메시지 집계 (Message Aggregation):
1. 첫 메시지 수신 시 30초 타이머 시작
2. 같은 사용자의 후속 메시지 수집
3. 30초 후 모든 메시지를 조합하여 하나의 질문으로 처리

## Acceptance Criteria

### AC1: 메시지 집계 상태 관리

DynamoDB 테이블 `AggregationState`가 생성되어 있고, 아래 스키마를 따른다:
- Partition Key: `pk` (String) = `{channel_id}#{user_id}`
- Sort Key: `aggregation_id` (String) = ISO 8601 timestamp
- Attributes: `messages` (List), `status` (String: AGGREGATING/COMPLETED/CANCELLED), `started_at`, `expires_at`, `message_count`, `ttl`
- TTL 활성화: `ttl` attribute (집계 완료 5분 후 자동 삭제)

[Source: docs/prd/epic-2-message-processing-pipeline.md#story-25-message-aggregation-30초-타임-윈도우]
[Source: docs/change-proposals/2025-12-24-message-aggregation-proposal.md#31-새로운-컴포넌트]
[Source: docs/architecture/tech-stack.md#dynamodb-테이블-aggregationstate]

### AC2: 집계 Repository 구현

`AggregationRepository` 클래스가 Shared Layer에 구현되어 있고, 아래 메서드를 제공한다:
- `get_active(user_key: str) -> Optional[AggregationState]`: 활성 집계 조회
- `get(user_key: str, aggregation_id: str) -> Optional[AggregationState]`: 특정 집계 조회
- `create(user_key: str, webhook_event: dict) -> AggregationState`: 새 집계 시작 (aggregation_id 포함)
- `add_message(user_key: str, aggregation_id: str, webhook_event: dict) -> AggregationState`: 메시지 추가
- `complete(user_key: str, aggregation_id: str) -> None`: 집계 완료 (상태: COMPLETED)
- `cancel(user_key: str, aggregation_id: str) -> None`: 집계 취소 (상태: CANCELLED)

[Source: docs/architecture/source-tree.md]

### AC3: SQS Delay Queue 생성

`AggregationTriggerQueue`가 SAM template에 정의되어 있고, 아래 설정을 따른다:
- DelaySeconds: 30 (기본 지연)
- VisibilityTimeout: 60
- MessageRetentionPeriod: 300 (5분)

[Source: docs/prd/epic-2-message-processing-pipeline.md#b-sqs-큐-aggregationtriggerqueue]
[Source: docs/architecture/tech-stack.md#sqs-큐-aggregationtriggerqueue]

### AC4: Worker Lambda 집계 로직

Worker Lambda가 SQS 메시지를 수신할 때 아래 처리 흐름을 따른다:

1. **메시지 유형 판별**:
   - `action == "FINALIZE_AGGREGATION"` → 집계 완료 처리
   - 일반 webhook 메시지 → 집계 로직 실행

2. **집계 로직 (일반 webhook 메시지)**:
   - `get_active(user_key)` 조회
   - 활성 집계 없음 → 새 집계 시작 + 30초 트리거 전송
   - 활성 집계 있음 → 메시지 추가
   - 이미지/파일 메시지 → 즉시 집계 완료 처리

3. **집계 완료 처리 (트리거 메시지)**:
   - `get(user_key, aggregation_id)`로 집계 조회
   - 집계가 없거나 `status != AGGREGATING`이면 무시 (중복/늦은 트리거 방지)
   - 집계된 메시지 조합 (`combine_messages()`)
   - 조합된 텍스트로 기존 RAG + LLM 파이프라인 실행
   - 집계 상태 완료 (`complete(user_key, aggregation_id)`)

[Source: docs/prd/epic-2-message-processing-pipeline.md#c-worker-lambda-로직-변경]
[Source: docs/change-proposals/2025-12-24-message-aggregation-proposal.md#32-worker-lambda-로직-변경]

### AC5: 메시지 조합 알고리즘

`combine_messages(messages: List[Message]) -> str` 함수가 구현되어 있고:
- 메시지를 timestamp 기준으로 시간순 정렬
- 줄바꿈(`\n`)으로 연결
- 최대 길이 제한 적용 (LLM 토큰 제한 고려)
- **최종 문의 텍스트는 500자 이하** (500자 넘으면 뒤에서 500자만 사용)

[Source: docs/prd/epic-2-message-processing-pipeline.md#253-요구사항]
[Source: docs/change-proposals/2025-12-24-message-aggregation-proposal.md#33-메시지-조합-알고리즘]

### AC6: Feature Flag 지원

Worker Lambda 환경 변수로 집계 기능 활성화/비활성화 가능:
- `ENABLE_MESSAGE_AGGREGATION` (true/false)
- `AGGREGATION_WINDOW_SECONDS` (기본: 30)
- `MAX_MESSAGES_PER_AGGREGATION` (기본: 10)

[Source: docs/architecture/tech-stack.md#feature-flag]

### AC7: 예외 처리

아래 예외 상황을 올바르게 처리한다:
- 단일 메시지만 수신: 30초 대기 후 정상 처리
- 타임아웃 후 추가 메시지: 새로운 집계 세션 시작
- 이미지/파일 메시지: 즉시 집계 종료 및 처리
- 최대 메시지 수 초과 (10개): 경고 로그 + 추가 메시지 무시

[Source: docs/prd/epic-2-message-processing-pipeline.md#255-예외-처리]

### AC8: 테스트 커버리지

아래 시나리오에 대한 테스트가 작성되어 통과한다:
- 단일 메시지 처리 (집계 불필요)
- 다중 메시지 처리 (5개 메시지, 30초 내)
- 타임아웃 후 추가 메시지 (새 집계 시작)
- 이미지 메시지 즉시 처리
- 최대 메시지 수 초과 처리

[Source: docs/architecture/coding-standards.md#test-strategy-and-standards]

## Dev Notes

### Architecture Context

**현재 아키텍처 (Before):**
```
Webhook → Ingest Lambda → SQS (WorkerQueue) → Worker Lambda → RAG + LLM → 응답
```

**변경 후 아키텍처 (After):**
```
Webhook → Ingest Lambda → SQS (WorkerQueue) → Worker Lambda
                                                    ↓
                                            [집계 로직 분기]
                                                    ↓
                                            DynamoDB (AggregationState)
                                                    ↓
                                            SQS (AggregationTriggerQueue, 30s delay)
                                                    ↓
                                            Worker Lambda (트리거 수신)
                                                    ↓
                                            [메시지 조합 + RAG + LLM]
                                                    ↓
                                                   응답
```

[Source: docs/architecture/tech-stack.md#아키텍처-패턴]

### Key Design Decisions

1. **타이머 관리: SQS Delay Queue 선택**
   - 대안: EventBridge Scheduler (동적 스케줄)
   - 선택 이유: 구현 단순, 비용 효율, Lambda 네이티브 통합
   [Source: docs/change-proposals/2025-12-24-message-aggregation-proposal.md#option-1-sqs-delay-queue-활용]

2. **집계 상태 저장: DynamoDB 선택**
   - 대안: Redis, In-Memory
   - 선택 이유: 서버리스 친화적, TTL 자동 삭제, 낮은 비용
   [Source: docs/architecture/tech-stack.md#메시지-집계-message-aggregation]

3. **Feature Flag 필수**
   - 롤백 가능성 확보
   - 점진적 롤아웃 지원
   [Source: docs/change-proposals/2025-12-24-message-aggregation-proposal.md#63-롤백-계획]

### Edge Cases & Error Handling

1. **동시성 이슈**: 동일 사용자가 동시에 여러 메시지 전송
   - 해결: DynamoDB 조건부 쓰기 (`ConditionExpression`)
   - 충돌 시: 재시도 또는 나중 메시지 무시

2. **타이머 중복 트리거**: 드물게 SQS 메시지 중복 전달
   - 해결: `status == AGGREGATING` 체크, 이미 완료된 집계는 무시

3. **집계 상태 누락**: DynamoDB write 실패
   - 해결: 활성 집계 없으면 새로 생성 (재시도 로직)

4. **이미지 메시지**: 텍스트 조합 불가
   - 해결: 즉시 집계 종료, 기존 텍스트 + 이미지 메타데이터로 처리

[Source: docs/change-proposals/2025-12-24-message-aggregation-proposal.md#62-엣지-케이스]

### Performance Considerations

**예상 추가 레이턴시:**
- 집계 대기: 최대 30초 (허용 범위)
- DynamoDB 읽기/쓰기: <10ms
- SQS 메시지 전송: <5ms
- **총 추가 지연: 30초 (타이머 대기)**

**예상 비용 절감:**
- LLM 호출: 66-80% 감소 (평균 3-5개 메시지 → 1회)
- (예시) 일 30건, 평균 3메시지 기준: 월 LLM 비용 -$0.40

[Source: docs/architecture/tech-stack.md#비용-추정-월간]

### Security & Compliance

- **PII 보호**: 집계 상태에 고객 정보 포함 (DynamoDB 암호화 필수)
- **TTL 자동 삭제**: 5분 후 자동 삭제로 데이터 최소화
- **로그**: aggregation_id만 로그, 메시지 내용 제외
