# Risk Profile - Story 5.3 (2025-12-25)

## 전체 판단

- **리스크 수준**: 중간(Medium)
- 이유: 로그/알림에는 개인정보(PII)가 섞일 수 있어서 실수했을 때 영향이 큽니다. 대신 마스킹 규칙이 코드로 고정되어 있고, 유닛 테스트로 보호되고 있습니다.

## 주요 리스크와 확인 결과

1. **SEC-001: Telegram/CloudWatch 로그로 PII가 새는 위험**
   - 상황: 고객 메시지에는 전화번호/이메일/카드번호 같은 PII가 들어올 수 있습니다.
   - 영향: 운영 로그에 PII가 노출되면 보안 사고가 됩니다.
   - 확인/조치:
     - `pipeline.py`에서 로그에 `mask_question()`/`mask_user_id()`를 사용합니다.
     - `build_sheets_log_row()`에서 `question_masked`는 `mask_question()`로 생성합니다.
     - 유닛 테스트로 전화번호/이메일/카드번호 마스킹을 확인했습니다.

2. **BUG-001: RAG 결과 타입 불일치로 Worker가 죽을 위험**
   - 상황: `retrieve_chunks()`는 `RetrievedChunk`(dataclass)를 반환하는데, 기존 코드가 dict처럼 다뤄서 런타임 에러가 날 수 있었습니다.
   - 영향: 메시지 처리 도중 예외가 나서 로그 기록/알림이 실패할 수 있습니다.
   - 확인/조치: `pipeline.py`에서 `RetrievedChunk.to_dict()`로 변환해 `SheetsLogRow`에 넣도록 수정했습니다.

3. **OPS-001: PROD 발송 결과 기록이 end-to-end로 아직 연결되지 않은 위험(낮음)**
   - 상황: `compute_action_taken()`은 “발송 성공/실패” 입력이 있을 때 `SENT/FAILED`를 만들지만, `pipeline.py`는 아직 실제 발송을 시도하지 않습니다(placeholder).
   - 영향: 운영에서 자동 발송이 붙었을 때 `action_taken`/`talktalk_send_result`가 기대와 다를 수 있습니다.
   - 제안(선택): Story 2.4의 `send_answer_if_allowed()`를 Worker 흐름에 연결하고, 성공/실패 케이스를 통합 테스트로 추가하면 더 안전합니다.
